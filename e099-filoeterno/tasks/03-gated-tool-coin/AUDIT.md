# Self-audit (model)

- [high] Centralized completion enables treasury drain: completeTask is owner-only with no criteria, multisig, timelock or verifier. Owner can submitTask to self (holds supply, meets MIN_HOLDING), complete it, and claimTask BOUNTY 50e18 from treasury. Any colluding submitter + owner can mint unlimited tasks and drain all fees/funding up to balance and allowance. Single owner compromise equals full pool loss. | fix: Add decentralized verification, require independent reviewer, cap total bounties, add per-task value, timelock, multisig owner, transferable ownership, and prevent owner/self submitter claiming.
- [high] Free Sybil task spam / ticket manipulation: submitTask only checks point-in-time balanceOf >= MIN_HOLDING and openCount <3, no fee, burn, stake or snapshot. Whale can split 5000e18 chunks to many Sybils and create unbounded taskCount. Holding can be flash-transferred in, submit, transferred out, transferred back for claim. MAX_OPEN is per-address only, not global. | fix: Require fee/burn/stake to submit, enforce snapshot or time-weighted holding, add global rate-limit/pause, max description length, and require holding continuously or slash.
- [medium] Censorship lock and owner griefing DoS: openCount increments on submit and only decrements on completeTask. No cancel, withdraw, timeout or dispute. Owner can censor a submitter by never completing, permanently locking them at MAX_OPEN=3. Conversely attacker Sybils force owner to pay gas per completeTask one-by-one with unbounded tasks. | fix: Add submitter cancel/expire after deadline, auto-decrement on claim, owner batch complete, pause, and dispute path.
- [medium] Treasury liveness dependency and immutable config: Treasury starts with 0 balance. claimTask reverts unless balanceOf[treasury]>=BOUNTY and allowance[treasury][address(this)]>=BOUNTY. If treasury never funds/approves, all claims DoS. No setTreasury/setOwner; lost/compromised treasury means fees sent to dead address forever and claims dead. Large blanket approval exposes full drain. | fix: Add setTreasury with zero-check + events + timelock, ownership transfer, pull-payment vault or pre-funded escrow per task, and limit allowance per claim with explicit approve flow.
- [low] CEI violation and non-standard treasury spend: claimTask does allowance-=, balance updates and emits before setting tasks[taskId].claimed=true. No external calls today so no reentrancy, but violates checks-effects-interactions. Direct allowance/balance manipulation bypasses transferFrom and standard events/allowance logic. | fix: Set claimed=true first, then update allowance/balances, or use internal _transferFrom/ _transfer. Add reentrancy guard.
- [low] Unbounded description storage bloat: submitTask only requires bytes(description).length>0 with no max length. Attacker can store huge strings per task, bloating state, raising submit/complete gas and enabling block-gas DoS at owner expense. | fix: Enforce max length e.g. 1000 bytes, store IPFS hash instead of full string.
- [info] Integer math rounding and zero-address gaps: Solidity 0.8.26 prevents overflow; amount*50/10000 safe for 1M supply. Fee truncates to 0 for amount<200 wei so dust is fee-free. _transfer blocks zero from/to and constructor blocks zero treasury, but approve allows zero spender and claimTask lacks explicit taskId range check (relies on zero-submitter revert). Self-transfer to self still takes fee to treasury. | fix: Document dust behavior, require spender!=0, require taskId>0 && <=taskCount in claimTask, emit events for config.
- [info] No reentrancy vector currently: No ETH, no external calls, all accounting internal. transfer/transferFrom/_transfer/complete/claim only update storage and emit. Safe from reentrancy unless future upgrades add external token calls. | fix: Keep CEI order, add nonReentrant on claim/transfer paths if extensible.
